blake3
------

```
go get github.com/forkcloser/blake3
```

`blake3` implements the [BLAKE3 cryptographic hash function](https://github.com/BLAKE3-team/BLAKE3).
The implementation aims to be performant without sacrificing (too much)
readability. Requires Go 1.26 or later.

In addition to the pure-Go implementation, this package also contains AVX-512
and AVX2 routines (generated by [`avo`](https://github.com/mmcloughlin/avo))
that greatly increase performance for large inputs and outputs on amd64. Every
other architecture runs the pure-Go code.

Three packages:

- `blake3` — `hash.Hash` (`New`, `Sum256`, `Sum512`, `DeriveKey`) and the
  seekable XOF (`Hasher.XOF`).
- `bao` — [Bao](https://github.com/oconnor663/bao) verified streaming:
  combined and outboard encodings, slices, and chunk-group verification.
- `guts` — the low-level tree-hashing primitives the two packages above are
  built on, for callers that hash their own trees.

## About this fork

A friendly fork of [lukechampine/blake3](https://github.com/lukechampine/blake3)
(import path `lukechampine.com/blake3`), taken at upstream `v1.4.1`, which is
also upstream's current `master`. The exported API is upstream's with two
additions (`guts.CompressBlocksN`, `bao.MaxGroup`) and one removal: the five
`Bao*` wrappers upstream kept in the root package after moving Bao to its
own package, already deprecated there, are gone; use package `bao`. For
everything else, switching is a change of import path.

What this fork fixes and adds that upstream does not have, each with the
change that landed it, is the table in [`UPSTREAM.md`](./UPSTREAM.md), beside
the fork point and what was taken from upstream since. The root package and
`bao` are held to ports of the specification's reference implementation
(`contract_test.go`, `bounded_test.go`), and upstream's suites retired under
a mutation score; the amd64 assembly is generated from `avo/gen.go` in its own
module, regenerated and compared by `just lint-generated`, and passes `go vet`.

Contributions that make sense upstream should go upstream first; see the
organization's [CONTRIBUTING](https://github.com/forkcloser/.github/blob/main/.github/CONTRIBUTING.md)
and [SECURITY](https://github.com/forkcloser/.github/blob/main/.github/SECURITY.md)
policies.

## Benchmarks

### This fork against upstream, same machine

Upstream `lukechampine/blake3` v1.4.1 (`dd9ffb9`, the fork point) and this
fork, measured 2026-09-07 with Go 1.26.5 on an Apple M5 Pro (darwin/arm64,
so the generic implementation; no SIMD paths run on this host). The two
were run interleaved, three rounds of `go test -run '^$' -bench . -benchmem
-count=2` each, and paired with `benchstat`; both use the same plain `b.N`
loop, since `b.Loop` alone costs ~2 ns per iteration and shows up as a false
4% on the 73 ns case. Lower is better; `~` means no statistically
significant difference. Upstream's write-size rows were noisier (up to
±51%) than the fork's (≤4%) in this run; the medians agree with two
earlier runs.

`BenchmarkWrite` alone, at io.Copy's 32 KiB, hid a 27% regression at exactly
that size in an earlier version of the write scheduler; the same file
compiled against upstream produced the upstream column.

## Shortcomings

There is no assembly routine for single-block compressions. This is most
noticeable for ~1KB inputs.

Each assembly routine inlines all 7 rounds, causing thousands of lines of
duplicated code. Ideally the routines could be merged such that only a single
routine is generated for AVX-512 and AVX2, without sacrificing too much
performance.

On amd64, the SIMD kernels always process a full 16-chunk (16 KiB) buffer: a
shorter eigentree tail is padded and the unused lanes' work discarded.

The AVX-512 kernels have not been executed since the fork. No CI runner has
`avx512f` (the amd64 legs report AVX2 only), the development machine is
arm64, and the fork changed the kernels' generator (the scalar broadcasts
now go through a register). The AVX2 kernels and the pure-Go code run on
every CI leg; the AVX-512 path is pinned by the same vectors but on a host
nobody has. TODO: run the test suite on an AVX-512 host, or under an
emulator that has it, before the next release that touches `avo/gen.go`.
