blake3
------

```
go get github.com/forkcloser/blake3/v2
```

`blake3` implements the [BLAKE3 cryptographic hash function](https://github.com/BLAKE3-team/BLAKE3):
hashing, keyed hashing, key derivation, extendable output, and Bao verified
streaming. The implementation aims to be performant without sacrificing (too
much) readability. Requires Go 1.26 or later.

In addition to the pure-Go implementation, this module contains AVX-512 and
AVX2 routines (generated by [`avo`](https://github.com/mmcloughlin/avo)) that
greatly increase performance for large inputs and outputs on amd64. Every
other architecture runs the pure-Go code. Every path is held to the official
test vectors and to a port of the specification's reference implementation,
on every CI run.

Three packages:

- `blake3`: a `hash.Hash` in each of BLAKE3's three modes (`New`, `NewKeyed`,
  `NewDeriveKey`), the one-shots (`Sum256`, `Sum512`, `Sum256Keyed`,
  `DeriveKey`), a seekable, random-access extendable output (`Hasher.XOF`),
  and a hash state that marshals and restores on any host.
- `bao`: [Bao](https://github.com/oconnor663/bao) verified streaming, as
  methods on an `Encoding` value: combined and outboard encodings, slices, and
  chunk-group verification.
- `guts`: the tree-hashing primitives the two packages above are built on, for
  callers that hash their own trees.

## Using it

```go
// A hash.Hash: 32-byte digest, any mode.
h := blake3.New()
if _, err := io.Copy(h, r); err != nil {
	return err
}
digest := h.Sum(nil)

sum := blake3.Sum256(data)                 // one call
mac := blake3.Sum256Keyed(key, data)       // key is a [32]byte
sub := blake3.DeriveKey("example.com 2026-11-12 session tokens v1", master, 64)

// Any amount of output, from any position, of everything written so far;
// ReadAt leaves the position alone and may run from several goroutines.
xof := h.XOF()
if _, err := xof.ReadAt(buf, 1<<20); err != nil {
	return err
}

// A long hash kept across processes, and continued anywhere.
state, _ := h.MarshalBinary()
var again blake3.Hasher
if err := again.UnmarshalBinary(state); err != nil {
	return err
}
```

```go
// Bao: the tree beside the data, so any prefix or slice verifies against
// the root alone. The zero Encoding is standard Bao.
enc := bao.Encoding{}
root, err := enc.Encode(dst, src, size) // dst is an io.WriterAt; root is Sum256(src)

// Streams the content to w as it verifies, and writes nothing it has not;
// content that does not match root is bao.ErrVerification.
err = enc.Decode(w, encoded, nil, root)

// A slice of the content anyone can verify with the root alone.
err = enc.ExtractSlice(sliceW, encoded, nil, offset, length)
err = enc.DecodeSlice(w, slice, offset, length, root)
```

## About this fork

A friendly fork of [lukechampine/blake3](https://github.com/lukechampine/blake3)
(import path `lukechampine.com/blake3`), taken at upstream `v1.4.1`, which is
also upstream's current `master`. The `v1` line of this module kept upstream's
API; `v2` departs from it where it was in the way:

- One constructor per mode, `New`, `NewKeyed` (a `[32]byte` key) and
  `NewDeriveKey` (streaming key derivation, which upstream has only as a
  one-shot), in place of `New(size, key)`; the digest is 32 bytes, longer
  output being the XOF's; `Sum256Keyed`, and `DeriveKey` returning its bytes.
- The hash state implements `encoding.BinaryMarshaler`, `BinaryUnmarshaler`
  and `BinaryAppender`, portable across hosts; the XOF implements
  `io.ReaderAt`.
- `bao` is methods on an `Encoding` value that names the chunk group and the
  layout, and a verification that fails is `bao.ErrVerification` rather than a
  `false` beside an error.
- `guts` is the tree primitives alone; the kernels and the scheduling that
  were exported with them are the module's own.

What this fork fixes and adds that upstream does not have, each with the
change that landed it, is the table in [`UPSTREAM.md`](./UPSTREAM.md), beside
the fork point and what was taken from upstream since. The root package,
`bao` and `guts` are held to ports of the specification's reference
implementation (`contract_test.go`, `bounded_test.go`), and upstream's suites
retired under a mutation score; the amd64 assembly is generated from
`avo/gen.go` in its own module, regenerated and compared by
`just lint-generated`, and passes `go vet`.

Contributions that make sense upstream should go upstream first; see the
organization's [CONTRIBUTING](https://github.com/forkcloser/.github/blob/main/.github/CONTRIBUTING.md)
and [SECURITY](https://github.com/forkcloser/.github/blob/main/.github/SECURITY.md)
policies.

The shape: a write under the kernels costs one kernel call per group of
sixteen chunks and nothing else up to 128 KiB, 0.28 µs a KiB under AVX-512
and 0.35 under AVX2 against 1.8 in pure Go, since `Write` holds a group back
and hands the kernels whole groups only (`Write`, at io.Copy's 32 KiB, is
6.4× pure Go under AVX-512); from 192 KiB a write's trees go to goroutines,
and at 1 MiB on this runner's four CPUs the kernels reach 6.6 and 4.4 GB/s,
1.5× each other and 5× and 3.3× pure Go. XOF output is the kernels' from the first
kilobyte, the block kernels filling eight or sixteen blocks at once, and the
two SIMD paths are equal there. Inputs of a chunk or less (`Sum256/64`,
`Sum256/1024`, `XOF/64`) never reach the kernels and are equal on every path.
Writes under 48 KiB allocate nothing; a 1 MiB write allocates ~4 KiB in 38
allocations, the goroutines' bookkeeping. A cloud runner is one machine on
one day; the run's raw output is the workflow's `bench-amd64` artifact, and
another dispatch produces another.

## Shortcomings

There is no assembly routine for single-block compressions. This is most
noticeable for ~1KB inputs.

Each assembly routine inlines all 7 rounds, causing thousands of lines of
duplicated code. Ideally the routines could be merged such that only a single
routine is generated for AVX-512 and AVX2, without sacrificing too much
performance.

On amd64, the SIMD kernels always compute a full group of 16 chunks (16 KiB).
`Write` hands them whole groups only, holding the input's last group back
until `Sum`, so the lanes run full while hashing; the held group at `Sum`,
and bao's chunk groups below 16 chunks, still pay a whole kernel for what
they hold.

No GitHub-hosted runner is guaranteed `avx512f`: the `ubuntu-24.04` pool
mixes hosts that have it with hosts that do not, and the development machine
is arm64. So the AVX-512 kernels run on every CI run under Intel SDE's
emulation (the `avx512` job, `just test-avx512-emulated`), which checks what
they compute and nothing about how fast; `just bench-amd64` times the real
kernels when its dispatch draws a host that has them, and stops, naming the
host, when it does not. The other two amd64 dispatch arms are required the
same way on every run (the `isa` job, `just test-isa avx2` and `just test-isa
generic`): the arm is forced through `GODEBUG`, and the suite passes only if
`TestRequiredISA` saw that arm taken, since the verify legs run whatever
kernels their host has and prove nothing about which.
